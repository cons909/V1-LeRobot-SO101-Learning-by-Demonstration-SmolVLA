# Automated Trial Harness — Design (as built)

Implements the flow from `EVALUATION_PROTOCOL.md`: 50 trials per model, video + timing + clamp
events + latency logged automatically, operator only grades the final outcome.

## Division of responsibility (unchanged from the existing production setup)

- **Mac** (`eval_harness.py`) — loads the checkpoint, does preprocessing/inference/
  postprocessing, drives the trial state machine, writes video files and the CSV log.
- **Raspberry Pi** (`pi_servers/robot_server_*.py`) — unchanged role: a ZMQ REP server that reads
  cameras + joint state on `get_obs`, and executes a requested action (with its existing safety
  clamp) on `action`. It has no concept of a "trial" — it just answers the same two requests it
  already answers in normal live inference.

## Files produced

| File | Role |
|---|---|
| `eval_harness.py` | Main Mac-side harness. Run 3x, once per `--model`. |
| `summarize_eval.py` | Builds per-model and cross-model results tables from the CSV logs. |
| `pi_servers/robot_server_side_claw_VERIFIED.py` | Unchanged copy of the verified side+claw Pi server. Already returns `action_sent`. |
| `pi_servers/robot_server_1cam_EVAL.py` | Adapted from `Smoth VLA/robot_server_new.py`: renamed `frame`→`front_frame`, added `action_sent` to the ack. Safety-clip logic untouched. |
| `pi_servers/robot_server_front_side_RECONSTRUCTED.py` | **Reconstructed, not original** — rebuilt from the side+claw server with cameras renamed to front/side. Camera indices are placeholders; confirm on the Pi before use. |
| `results/<model>/trial_log.csv`, `results/<model>/videos/`, `results/<model>/summary.md` | Generated by running the harness — not created yet, appear on first run. |

## Per-trial flow (as implemented)

1. Operator resets the environment during an 8-second countdown (`RESET_COUNTDOWN_S`).
2. Recording + timer start automatically once torque re-engages.
3. Loop: request obs from Pi → write camera frame(s) to that trial's video file(s) → run
   through the checkpoint's preprocessor/policy/postprocessor → send the action → receive
   `action_sent` back.
   - Clamp event: `max(|requested - action_sent|) > CLAMP_TOLERANCE` (0.5 by default).
   - Loop latency: measured directly from the request/response round trip.
   - Trial-end check: the operator presses `n` the moment they judge the attempt is over —
     there is no proximity-to-home requirement, the arm can be anywhere (`stop_reason =
     manual_end`). A 120s timeout (`TRIAL_TIMEOUT_S`) is the only automatic backstop
     (`stop_reason = timeout`). `q` quits the whole session instead of ending just the trial.
4. Torque releases immediately either way. Ended by `n` → the operator is prompted to grade it
   1-4 against the full rubric. Timed out → a reduced 3-choice question instead (completed but
   too slow / grasped or touched it but didn't finish / never touched it) → logged as
   `timeout_success_slow` / `timeout_grasped` / `timeout_no_touch`, with duration recorded at
   the max time. The arm is **not** auto-moved anywhere on a timeout — the operator repositions
   it by hand, same as any other trial end.
5. Row appended to `results/<model>/trial_log.csv`.
6. The next reset countdown starts immediately after logging — no extra confirmation step
   between grading and the countdown. Repeat for 50 trials (or `q` during a trial to quit early
   — partial logs are still usable).

Run `python summarize_eval.py --model <name>` after a session, or `--all` once all three models
have been run, to generate the results tables for the README.

## Compatibility audit (2026-08-13)

Checked `eval_harness.py` line-by-line against the actual `lerobot` source in this project
(`lerobot/src/lerobot/robots/so_follower/so_follower.py`, `policies/utils.py`,
`policies/factory.py`, `policies/smolvla/modeling_smolvla.py`) and against all three Pi server
variants. Two real bugs found and fixed:

1. **`action_sent` was assumed to be an array; it's actually a dict.** `robot.send_action()`
   returns `{"shoulder_pan.pos": val, ...}`, not a flat array — confirmed directly in
   `so_follower.py`. The side+claw and reconstructed front+side servers forward that dict as-is.
   `PiClient.send_action()` now detects a dict and rebuilds the `(6,)` array from it in `JOINTS`
   order; the 1-camera server's plain-array `action_sent` still works via the same code path.
2. **No reconnect after a ZMQ timeout.** A REQ socket that times out on `recv()` is stuck and
   rejects the next `send()` — this is exactly why the reference `run_smolvla_live.py` has its
   own `reconnect_socket()`. The original harness caught the timeout but kept reusing the same
   socket, which would have silently stalled every request after the first dropped response.
   Fixed by moving all socket handling into a `PiClient` class that reconnects automatically.

Everything else checked out: camera dict keys (`obs["side"]`, `obs["front"]`, etc.) match what
`get_observation()` actually populates them as; `prepare_observation_for_inference` /
`make_pre_post_processors` / `select_action` signatures match the harness's usage exactly;
video color handling (write BGR, keep RGB for policy input) matches the report's established
convention.

**Second pass (same day):** two more fixes, neither would have crashed a run but both would
have degraded the evidence quality:
3. **Video fps was hardcoded to 10.0**, but the real inference loop rate depends on actual
   SmolVLA/MPS speed and network round-trip, which could easily be slower — the saved videos
   would then play in fast-motion, not matching the logged (correct) wall-clock duration. Fixed
   by buffering frames in memory during the trial and encoding the video afterward at the
   *actual* measured fps (`frame_count / duration`). Trade-off: a worst-case ~60s two-camera
   trial buffers roughly 1GB in memory, released immediately after each trial — fine on this
   machine, noted directly in the code.
4. **No manual-override check while retrying a failed `get_obs`.** If the Pi became briefly
   unreachable, the retry loop had no way to honor `e`/`q` and would just wait out the full
   60s timeout. Fixed: the retry branch now polls for the same override keys as the main loop.

**One methodological caveat worth flagging in the eventual writeup, not a bug:** "clamp events"
don't mean quite the same thing across all three models. For `side_claw` and `2cam`
(reconstructed), a clamp event means the robot's built-in `max_relative_target` capped a
too-large single-step movement. For `1cam`, it means the custom `SAFE_LIMITS` logic capped a
joint that was heading past its absolute safe range — a different safety mechanism entirely.
Both get counted the same way in the CSV (`requested vs. action_sent` diff), but they're not
strictly apples-to-apples if you want to make a claim like "model X caused more clamp events
than model Y" — worth a one-line caveat in the results section rather than treating it as a
clean comparison.

## Torque release between trials (added after the first dry run)

The dry run surfaced a real gap: the deployed Pi server has `disable_torque_on_disconnect=False`
and no command to release the servos, so there was no way to reset the physical environment
between trials without fighting the still-engaged motors. Fixed by adding a `torque` command to
every Pi server variant (`{"cmd": "torque", "enable": bool}` → calls `robot.bus.enable_torque()`
/ `disable_torque()`), and wiring the harness to call it automatically: released the instant a
trial ends (and during the reset countdown), re-engaged right before the next trial starts. Also
released on server shutdown now (previously it wasn't, matching the `disable_torque_on_disconnect
=False` setting — that flag still governs disconnect behavior, but shutdown now explicitly
releases torque first as an extra safety step).

**This means `robot_server_side_claw_VERIFIED.py` is no longer what should be running for actual
eval sessions** — it's kept as an unmodified historical copy of what produced the original
report's results. Use `robot_server_side_claw_EVAL.py` instead (same file, +torque command) for
anything driven by `eval_harness.py`, including the next dry-run attempt. `1cam_EVAL` and
`front_side_RECONSTRUCTED` already had the command added in place.

## Pi-side deployment findings (2026-08-17, verified working)

Confirmed on the real Pi: `robot_server_side_claw_EVAL.py` running as `~/robot_server_eval.py`
responds correctly to `ping`, `get_obs`, and `torque` (both directions), and the side_claw
checkpoint loads cleanly on MPS. Full narrative in `Backgroud information/
08_Eval_Harness_Pi_Deployment_Archive_2026-08-17/session_log_2026-08-17.pdf` (canonical copy:
`session_log_2026-08-17.pdf` in this folder). Two things to know before running real sessions:

- **Intermittent servo-bus lock.** Happened once, not yet reliably reproducible: `get_obs` can
  fail with `"Port is in use!"` if the underlying servo SDK's `is_using` lock gets stuck true
  after an interrupted transaction (e.g. a transient USB hiccup). `PiClient.reconnect()` fixes
  the *ZMQ* connection but not this — it's a lock inside the Pi process's servo bus, so the only
  fix is restarting the Pi server itself. If `get_obs` starts failing repeatedly with exactly
  that message during a session, that's the signal to restart `robot_server_eval.py` on the Pi.
- **Stop the Pi server with `Ctrl+C`, not `kill`.** The cleanup that releases torque
  (`robot.bus.disable_torque()`) only runs inside `except KeyboardInterrupt`, which `SIGTERM`
  does not trigger. A `kill`ed server can leave torque engaged.

## Manual trial-end redesign (2026-08-17, after the second dry-run attempt)

The original design auto-detected trial end via proximity to a captured home pose
(`DEPART_THRESHOLD`/`RETURN_THRESHOLD`/`RETURN_DWELL_S`), plus a scripted active return-to-home
on timeout. The user asked for both to be removed: a completed pick-and-place doesn't need to
end at any exact position, so requiring proximity to "home" to auto-close a trial was the wrong
mechanism entirely — replaced with the operator pressing `n` the instant they judge the attempt
over, watching it directly rather than the harness inferring it from joint angles. The scripted
timeout-driven return-to-home was also removed per explicit request — on a timeout the arm now
just releases torque in place, same as any other trial end, and the operator repositions it by
hand. Net effect: `home_pose` capture, `DEPART_THRESHOLD`, `RETURN_THRESHOLD`, `RETURN_DWELL_S`,
`RETURN_TO_HOME_TIMEOUT_S`, `RETURN_TO_HOME_TOLERANCE`, `capture_home_pose()`, and
`return_to_home()` are all gone from `eval_harness.py` — dead code once both use sites were
removed, not left dormant. The manual-end key changed from `e` to `n` to match, and the separate
post-grading "type n to continue" gate from the previous revision was folded into this same `n`
press (ending the trial *is* the confirmation now — no second gate).

## Real hardware safety incident (2026-09-02) — motor overheating, fixed

During a 2cam session on `robot_server_front_side_RECONSTRUCTED.py`, a wrist motor overheated
(burning smell, motor visibly stiffer even after power was disconnected). Root cause: **neither
the side+claw nor the reconstructed front+side server had any motor-load safety check at all**
— only the robot's per-step angle clamp (`max_relative_target=15°`), which limits how far a
single command can move a joint but does nothing to stop sustained high current if the arm is
pushed against a mechanical limit or obstruction across many consecutive steps. The 1cam server
already had this protection (ported from `Smoth VLA/robot_server_new.py`); the other two never
did.

**Fixed by porting the same HOLD/E-STOP load monitoring into both `robot_server_side_claw_EVAL.py`
and `robot_server_front_side_RECONSTRUCTED.py`:** every action now reads `Present_Load` first;
≥68% of rated torque skips that action (HOLD), ≥88% disables torque entirely and requires an
explicit `reset_estop` command (E-STOP) — identical thresholds and logic to the 1cam server.

**Also fixed: E-STOP was invisible from the Mac side.** Previously, once tripped, every
subsequent action would just get silently rejected — the arm stops moving with nothing printed
anywhere, which is genuinely how the overheating incident went unnoticed until physical damage
was visible. All three harness files (`eval_harness.py`, `eval_harness_1cam.py`,
`eval_harness_2cam.py`) now detect an E-STOP ack, print it loudly, and automatically call
`reset_estop` + retry the action once — falling back to a clear "restart the Pi server" message
if that doesn't clear it. A rejected action for any reason now always prints a warning in
`run_trial()` instead of failing silently.

**Before running any further sessions on any model:** redeploy the updated `robot_server_
side_claw_EVAL.py` and `robot_server_front_side_RECONSTRUCTED.py` to the Pi (`robot_server_
1cam_EVAL.py` already had this). Physically inspect the hardware for damage from the incident
before applying power again — this fix prevents a recurrence, it does not undo damage already
done.

## Before running for real

1. **Confirm `PI_IP`** at the top of `eval_harness.py` — set it to your Pi's current address
   (update if it has changed since you last checked).
2. **Start the matching Pi-side server first**, for the model being evaluated:
   - `1cam` → `robot_server_1cam_EVAL.py`
   - `2cam` → `robot_server_front_side_RECONSTRUCTED.py` (confirm camera indices first — see
     the TODOs in that file)
   - `side_claw` → `robot_server_side_claw_EVAL.py` (not `_VERIFIED.py` — see "Torque release
     between trials" above for why)
3. All three Pi server scripts are drafts living in `Publicacion github/pi_servers/` — you'll need
   to copy the correct one onto the Pi yourself before starting a session (no direct Pi
   filesystem access from this side).
